WHAT CANNOT BE VERIFIED (LIMITATIONS DOCUMENTED):
==================================================

1. Graph Engine SHA Verification (Not Possible)
   - Graph-doc-gen does not store SHA metadata on nodes
   - Cannot query "which SHA is this graph for?"
   - Mitigation: Checkpoint keying prevents cross-SHA reuse
   - Status: Accepted (no external repo modifications)

2. Complete Sync Detection (Partial Sync Risk)
   - Node count check proves "not empty" but not "complete"
   - If sync fails mid-way, nodes exist but incompletely
   - Mitigation: Accepted as known limitation
   - Status: Out of scope for Phase 1

3. Stale Graphs Within Same SHA (Rare Case)
   - Cannot distinguish first sync from second sync to same SHA
   - Mitigation: Graph engine responsible for deterministic parsing
   - Status: Graph engine responsibility


HOW VERIFICATION PREVENTS SILENT STALE REUSE:
==============================================

Scenario A: Correct Behavior (Different SHA)
─────────────────────────────────────────────
Time 1: process_commit(repo_x, SHA-A)
        → CheckpointManager.get(repo_x, SHA-A) → not found
        → GraphAdapter.sync_to_sha() → creates nodes
        → CheckpointManager.save(repo_x, SHA-A, COMPLETE)

Time 2: process_commit(repo_x, SHA-B)  [DIFFERENT SHA]
        → CheckpointManager.get(repo_x, SHA-B) → not found
           [Because key (repo_x, SHA-B) ≠ (repo_x, SHA-A)]
        → GraphAdapter.sync_to_sha() → syncs to SHA-B
        → CheckpointManager.save(repo_x, SHA-B, COMPLETE)
        
Result: ✅ Two independent checkpoints, no stale reuse


Scenario B: Old Behavior Without Keying (Silent Reuse Risk)
──────────────────────────────────────────────────────────
[If checkpoint was keyed only by repo_id without SHA]

Time 1: process_commit(repo_x, SHA-A)
        → Checkpoint(repo_x) → not found
        → sync_to_sha() → creates nodes
        → Checkpoint.save(repo_x, COMPLETE)

Time 2: process_commit(repo_x, SHA-B)  [DIFFERENT SHA!]
        → Checkpoint(repo_x) → FOUND (from SHA-A!)
        → REUSE from cache without re-syncing
        → Nodes are stale for SHA-B
        → Silent error: graph is for SHA-A, but API claims SHA-B
        
Result: ❌ SILENT STALE REUSE - THIS WAS THE GAP


With Keying (Phase 1 Correction):
─────────────────────────────────
Checkpoint key includes both repo_id AND target_sha
→ (repo_x, SHA-A) ≠ (repo_x, SHA-B)
→ Cannot accidentally reuse SHA-A checkpoint for SHA-B request
→ Different SHAs always get separate checkpoint queries
→ Prevention at database key level (SQL PRIMARY KEY)
